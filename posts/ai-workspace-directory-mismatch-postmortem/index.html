An AI Workspace Mix-Up: How Captain Noodle's Notes Landed in Disco Potato

PUBLISHED 2026.10.10 10 MIN READ — VIEWS #AI Agents#ChatGPT#Codex#Workspace Isolation#Incident Response

My project was Captain Noodle, but the assistant saved its notes in Disco Potato. The project had not been renamed. Chat membership and the local working directory had diverged—and the assistant treated execution context as user intent.

Anonymization note: Project names, chat names, and the notes filename are fictional aliases, not actual renames. Device details have been generalized, and incident dates and times are expressed as relative order. The factual relationships and investigation conclusions remain unchanged. The date displayed on this page is the article's publication date, not the incident date.

TL;DR

In one sentence:

Being able to write to a directory does not mean the user wants this content saved there.

1. One notes file exposed a mismatch between two projects

I created a ChatGPT project named Captain Noodle to turn idle computers into a home development and services environment.

To keep the discussions focused, I used several chats: Sock Drawer, Deploy-o-Saurus, and Hamster Gym. During the discussion, I asked the assistant to save a passage of notes as snack_notes.md and keep appending future entries.

The assistant reported that the file had been saved. Its link, however, pointed to another existing project: Disco Potato.

That raised an obvious question:

My project is Captain Noodle. Why did its notes end up in Disco Potato?

I clarified that this was a ChatGPT project, that I had not configured that local directory for it, and that I could not find the directory-setting entry the assistant described.

The investigation could not stop at the visible symptom: two different names. It needed to answer four separate questions:

  1. Which project does the application currently assign this chat to?
  2. Which directory does the local executor actually use?
  3. When did that directory enter the chat's execution context?
  4. What evidence explains the initial selection—and what evidence does not?

2. No project rename: three identities must stay separate

Cross-checking the application project list and chat execution records produced the following relationship:

Object Recorded identity File access
Captain Noodle ChatGPT project The returned project record had no local directory field
Disco Potato Separate local project Associated with another existing directory
Hamster Gym chat Local Codex execution thread assigned to Captain Noodle Its working directory still pointed to Disco Potato

Three concepts matter here:

  • Project membership: Which project the application assigns the chat to.
  • Execution mode: Which executor runs the chat and whether local tools are available.
  • Working directory: Where those tools actually read and write files.

“The chat belongs to Captain Noodle” does not imply that its local working directory is Captain Noodle. Local tool access also does not establish that the user converted the project to Work.

OpenAI's official documentation distinguishes shared sources in ChatGPT projects from folder access in local projects, and describes chats retaining their recorded working directory. That clarifies the concepts; it does not establish the specific trigger in this incident. Official project and chat documentation

3. Investigation method: trace current state back to creation

Current state can establish a mismatch, but cannot by itself explain how it arose. The investigation continued through local session creation records, read-only database queries, and desktop client logs.

Two principles guided the checks:

  • Cross-check records: Do session metadata and client request logs identify the same creation or fork event?
  • Trace backward in time: Did the wrong directory appear when the notes were saved, or was it already present?

The chat aliases distinguish sessions; they do not imply that those sessions had these names at creation.

Order Event What the records establish
Day one, initial creation Sock Drawer chat created The creation record already contained the Disco Potato directory; the client used a local execution environment
Day one, later Deploy-o-Saurus forked from the previous chat The fork-source field identifies the parent; the directory stayed the same
Day two Hamster Gym created through another fork The parent relationship is confirmed again; the directory still stayed the same
Afterward Assistant answered a cross-chat access question It mistook the working directory's name for project identity
Later Notes saved as requested The file and persistent append rule were written into the other project's directory
After the user raised the discrepancy Project membership and execution records cross-checked The directory association predated the notes write and remained after two forks

This rules out one explanation:

Saving the notes was not the operation that first associated the chat with the other project's directory.

That directory was already present when an earlier chat was created, and remained in its descendants.

There are two distinct layers.

4.1 Project membership and working directory diverged

The current project membership and local session directory point to different objects. That is directly supported by the records.

The investigation did not recover the complete history of project membership changes. It therefore cannot establish that the chat was created first and moved into the project later, or that it was created directly from that project. The diagram describes observed relationships; it does not invent missing UI actions.

4.2 The assistant failed to recognize the mismatch and amplified it

The assistant treated the directory name as the project name and introduced background from the other project. When asked to save a file, it assumed that the current working directory was the right destination.

“The environment supplied the wrong directory” is not enough to explain away that responsibility.

The execution environment tells the assistant where it can operate. The user's request tells it what outcome it should achieve. A destination check is still needed between the two.

Interpreting execution context as user intent was the assistant's judgment error.

5. Root-cause boundary: propagation is clear, the initial trigger is not

The earliest creation record shows that the client created a locally executed chat and used the Disco Potato directory.

The available logs do not capture the complete UI interaction or preserve a parameter chain sufficient to explain the initial directory selection.

Candidate explanation Evidence boundary
The client reused a previous directory or composer state Creation-time state is missing; current state cannot reconstruct it
The creation entry point or membership handling had a client defect The complete selection path and a controlled reproduction are missing
The user selected a directory through some entry point The user says they did not configure it; the logs do not prove such a selection
The chat was assigned to the project later while retaining its directory This can explain the state, but the timing of that membership change was not recovered

Two overreaches are especially tempting:

  • Turning “the client submitted this directory” into “the user configured this directory.”
  • Turning “a state mismatch was observed” into “a specific product defect has been proven.”

Neither is supported by the available evidence.

Further localization requires creation-time directory-selection parameters, the UI state at that time, or a controlled reproduction in an isolated directory. Product support should receive anonymized key fields, not complete local logs.

The propagation mechanism is confirmed; the trigger for the initial directory selection remains unresolved.

6. Actual impact—and conclusions the evidence does not support

Confirmed effects include:

  • The current discussion acquired background from another project.
  • snack_notes.md was saved in the other project's directory.
  • The persistent append rule was written into that project's workspace instructions.
  • Related discussion entered that project's conversation record.

This does not establish a project rename, conversion to Work, or a cross-account permission breach.

During the incident investigation, no application database was modified, no chat directory was rebound, and no existing notes were moved or deleted. That stage also made no GitHub commits, pushes, or publications. It consisted of relevant read-only checks and review materials.

Detecting a mismatch and fixing it must be reported separately. The prevention measures below are not a claim that a fix has already been implemented.

7. Prevention checklist: keep the next notes file from wandering off

Check the project, directory, and destination before writing

Before saving a project file, establish separately:

  1. The project and outcome the user means.
  2. The executor's current working directory.
  3. The destination intended for this particular file.

If they disagree, resolve the destination. Do not guess from a directory name.

Check execution context when forking—not just the topic

A fork can retain history and may retain execution context. A plausible chat name and project membership do not establish that the working directory is correct.

For a discussion-only request, an in-chat Markdown draft can come first. If a local file is required, confirm its destination.

Separate permission checks from intent checks

Sandbox access answers a permissions question. Whether the user wants this content in that directory is an intent question.

Permission validation cannot replace checks of project identity and write destination.

Leave room for uncertainty

A credible postmortem should state:

  • Confirmed facts.
  • Evidence-supported explanations.
  • Hypotheses still awaiting validation.
  • The evidence needed to continue.

“Not fully established” is not a failed investigation. Packaging an unknown as a fact is what creates the next error.

8. Conclusion: Captain Noodle did not become Disco Potato

Captain Noodle did not become Disco Potato.

What happened was a mismatch between chat membership, execution mode, and the local working directory. The old directory was present when the earliest relevant chat was created and remained after two forks. The assistant then treated execution context as user intent, and the notes landed in the wrong place.

Why that directory was initially selected still requires more evidence.

For an AI assistant that can read and write files, answering correctly is only the first step. It must also establish:

Which project am I working for, and where will I put the result?

Sources and evidence boundaries

  • This article draws on first-hand records from a real incident and has been anonymized. Original session identifiers, logs, personal paths, and real names are not public.
  • OpenAI: Projects and chats explains the project/directory concepts; it is not evidence that this incident's initial trigger has been established.
  • This is a single-incident report of a confirmed mechanism and investigation limits, not a claim that the behavior applies to every project, chat, or client version.
