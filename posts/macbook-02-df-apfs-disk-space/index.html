MacBook Best Practices 02: Understanding df -h and APFS Disk Space

PUBLISHED 2026.10.22 9 MIN READ — VIEWS #MacBook#Terminal#APFS#Disk Space#df#du

💻 You run df -h on a MacBook to check free storage. Several rows show the same 926Gi capacity and 484Gi available, while two others report 100%. Has the disk filled up, and how many disks are there?

In this example, the main APFS container has about 926Gi of capacity and 484Gi remaining. The repeated figures belong to volumes sharing space. The two special filesystems reporting 100% do not establish that the storage disk is full.

This is part 02 of the MacBook Best Practices series. It explains macOS storage statistics through an actual terminal report. The numbers describe that captured state; documentation and local command manuals were checked on October 22, 2026. Device identifiers and auxiliary-volume layouts vary across computers and macOS versions.

1. What does df -h inspect?

df -h

df reports space statistics for mounted filesystems. Without a path argument, it normally lists the mounted filesystems. -h makes capacity figures easier to read. The macOS df(1) manual documents its options and accounting.[1]

In this terminal line:

➜  ~ df -h

➜ ~ is the shell prompt. The tilde represents the current user's home directory; the command itself is just df -h.

The units also matter:

Display Meaning
Ki Units of 1,024 bytes, or KiB
Mi Units of 1,024² bytes, or MiB
Gi Units of 1,024³ bytes, or GiB
Bi Bytes

Capacity columns use powers of 1,024 with df -h, whereas df -H uses powers of 1,000. Storage vendors typically advertise decimal GB and TB. One GiB is approximately 1.074 GB, so the numbers are not directly interchangeable.

Mounted on Mount point The location where the filesystem joins the directory tree

An inode is roughly a record describing a filesystem object, such as a file or directory. It is not strictly a count of ordinary files. With APFS, ifree should not be treated as a direct prediction of how many more files can be created. For everyday storage checks, start with the capacity columns.

A mount point connects a filesystem to a directory. / is the root of the directory tree, but filesystems mounted beneath it have their own accounting. The root row's 13Gi therefore does not represent all data on the Mac.

3. Why do several rows show 926Gi?

The key distinction is between an APFS container and its volumes.

Multiple volumes in one container draw from a common free-space pool. When one grows, less space remains for the others. Apple's APFS volume guide explains this allocation model.[2]

For this report, the relationship is approximately:

Main APFS container: about 926Gi
├─ Data volume       about 416Gi used
├─ System volume     about  13Gi used
├─ Preboot           about  10Gi used
├─ VM                about   2Gi used
├─ Recovery, Update, and other overhead
└─ Shared remaining space: about 484Gi

Do not add the repeated 926Gi capacities or count the shared 484Gi more than once. Subtracting Data's 416Gi from 926Gi does not yield 484Gi, because other volumes and filesystem overhead also consume container space.

Using the rounded figures, the main container has approximately:

926Gi - 484Gi ≈ 442Gi used
442 ÷ 926 ≈ 48%

This is a container-level estimate, not an exact account of every partition on the physical SSD. Use diskutil apfs list for a fuller container report.

4. Why does Capacity show 47%?

For this shared-space report, macOS df uses the following relationship:[1]

Capacity = volume used space ÷ (volume used space + available space)

For Data, the displayed numbers give:

416 ÷ (416 + 484) ≈ 46.2%

df normally rounds percentages upward, while the capacity figures themselves have also been rounded. That explains the displayed 47%; the human-readable figures cannot reconstruct the underlying accounting exactly.

These calculations answer different questions:

Calculation Question answered
416 ÷ 926 ≈ 45% Approximately what share of total container capacity does Data occupy?
416 ÷ (416 + 484), displayed as 47% What usage figure does df report for Data?
(926 - 484) ÷ 926 ≈ 48% Approximately how much of the main container is occupied overall?

To judge remaining writable space, prioritize Avail and inspect the container. A single volume's Capacity is not a universal SSD usage percentage.

5. What are all these system volumes?

Modern macOS separates system files from changing data. Apple's Role of Apple File System describes the principal volumes and explains that macOS 11 and later boot from a system snapshot.[3]

Mount point or name Practical interpretation
/ System root; this report's disk3s3s1 is the mounted system snapshot
/System/Volumes/Data Changing data, including user files, user-installed applications, and much runtime data
/System/Volumes/VM Swap files; the reported usage is disk space, not installed RAM
/System/Volumes/Preboot Supporting data needed during startup
/System/Volumes/Update A system-update-related volume
/Volumes/Recovery Recovery-system volume
xarts, iSCPreboot, Hardware Internal auxiliary volumes related to startup, security, or hardware support; df alone cannot fully establish their individual roles
/System/Volumes/Update/SFR/mnt1 An auxiliary mount beneath the update directory; its precise origin cannot be established from this row alone

Device numbers are identifiers, not a list of purchased drives. For example, disk3 can identify a synthesized APFS container; suffixes distinguish volumes or other slices. Use diskutil list and diskutil info to establish the actual hierarchy and device origin.

6. Do the two 100% entries require action?

devfs          ... 100% ... /dev
map auto_home  ... 100% ... /System/Volumes/Data/home

devfs is a virtual filesystem presenting device nodes. map auto_home is an automounter mapping entry. Neither is an ordinary storage volume whose capacity percentage can be interpreted like the Data volume's.

In this report, these two 100% values are not evidence that the storage disk is full. The relevant storage volumes and container still report approximately 484Gi available.

7. From remaining capacity to large directories

Use the tools together: df reports filesystem space; du measures the usage of selected files or directories. The following commands inspect information.

Check the filesystem containing your home directory

df -h ~

This checks the filesystem containing your home directory, not the home directory's own size. To hide the inode columns, add uppercase -I:

df -h -I ~

Measure your home directory and its immediate subdirectories

du -sh ~
du -h -d 1 ~ | sort -h

The first command reports a total. The second lists directories one level deep and sorts the human-readable sizes from smallest to largest; it also includes the home-directory total. -d 1 limits the reporting depth, but deeper contents still need scanning, so a large directory can take time.

If Operation not permitted or Permission denied appears, some directories were unreadable and the result may be incomplete. Directory totals from du also need not match APFS container usage. Scan scope, permissions, snapshots, and shared blocks affect the comparison.

Inspect disks, containers, and volumes

diskutil list
diskutil apfs list

To investigate the final mount in this particular report:

diskutil info /dev/disk2s1

That identifier belongs to this example. On another computer, or after mounts change, find the current identifier with diskutil list first.

Read your local manuals

man df
man du
man diskutil

Press q to exit. macOS utilities may accept different options from the GNU versions commonly found on Linux; check the local manual when adapting commands.

8. A practical reference

What you want to know Command
Space across mounted filesystems df -h
Remaining space on the filesystem containing home df -h -I ~
Space used by the home directory itself du -sh ~
Which immediate home subdirectories are large du -h -d 1 ~ | sort -h
Disk, partition, and container relationships diskutil list
APFS container space allocation diskutil apfs list

For a report like this one, start with Data's Avail, confirm the APFS container structure, and then use du to investigate particular directories. That sequence gives a more useful reading than adding every capacity row or reacting to an isolated 100%.
