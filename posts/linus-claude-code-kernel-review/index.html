Review Responsibility in Linus Torvalds and Claude Code Kernel Work

PUBLISHED 2026.10.15 6 MIN READ — VIEWS #Claude Code#Linux#Code Review#Concurrency

Reading InfoQ's account of Linus Torvalds using Claude Code to optimize the Linux page cache, I was most interested in the complete development process: AI helped produce an implementation and tests, Linus reported measurements from his machine, maintainers identified a race during public review, and the patches continued to evolve.

That sequence shows both the value of AI assistance and the difficulty of verification. A tool can contribute deeply to complex systems development while code that runs quickly and has undergone testing and initial review still violates a concurrency requirement.

My conclusion is that teams adopting AI coding tools should make each correctness claim, its supporting evidence, and its acceptance owner more explicit.

What the patches change

The optimization addresses contention when many threads repeatedly read a small part of the same file. A folio is a unit of memory management used for cached file data. Taking and releasing references modifies a shared counter, so even readers can compete over writes to the same cache line. Linus: Reading the page cache without folio references

Linus disclosed that Claude Code assisted with code, test programs, review, and the initial explanatory text under his direction; measurements ran on his machine. The early description lists eight patches. The rcu-free-v3 series discussed publicly on October 13 contains ten. Results need to remain attached to their versions. Linus: Patch description, Linus: Improve page refcount scalability

In the later Threadripper microbenchmark, throughput at 64 threads rose from 13.3 million to 304 million reads per second, roughly 23 times the baseline. Linus explicitly qualified the result: all CPUs repeatedly read a small region of one page, and real workloads would benefit much less. Linus: Benchmark results and conditions

The result exposes a scalability limit caused by a shared counter. Evaluating its value for a database, build, or production service requires measuring that workload.

Memory lifetime and file state need separate checks

The proposed fast path avoids folio reference operations by using RCU to defer memory reclamation. RCU separates removing an object from a data structure from reclaiming its memory, waiting for existing readers to leave the relevant critical sections before reclamation. Linux documentation: What is RCU

This reduces synchronization work for readers. It also leaves a separate question: while the memory remains accessible, does it still correspond to the file state used by this read?

Kiryl Shutsemau identified a race in filemap_read_rcu_batch(). His email gives this interleaving, simplified here:

Step Reader Other thread
1 Finds old folio A and validates its cache slot
2 Evicts A; RCU defers reclaiming its memory
3 Writes, repopulates the cache, and extends the file
4 Reads the new i_size but copies from old A

The reader combines an old data object with the updated file length and can return data never written at the corresponding location. Keeping the old memory alive does not establish correct file-read semantics. Kiryl: Race analysis and interleaving

Linus suggested moving the size read earlier and consolidating the cache-slot validation. Kiryl's revision explains the required flag checks, barriers, and ordering, while retaining the data-readiness check. Linus: Proposed ordering change, Kiryl: Revised patch and ordering explanation

This is valuable concurrency review: establish when each observation is valid, then determine whether those observations can safely be used together. Application systems face related problems when an old permission decision authorizes a new request, or a stale inventory snapshot is used for a later deduction.

How I read the article's conclusion

I agree with the article's recommendation to retain human code review. A maintainer supplied a concrete counterexample and helped move the patch forward.

Framing the story around even an expert missing a bug can obscure how the work proceeds. Complex concurrent code benefits from multiple reviewers because experience, tests, and different reasoning approaches complement each other. Here, Linus proposed an adjustment and Kiryl explained and revised it. Review helped complete the design.

The case also cannot establish an AI-versus-human defect rate. That comparison would require similar tasks, comparable testing and review effort, and enough observations. One missed race shows that the available evidence failed to cover an interleaving; it cannot characterize every AI-generated implementation.

The working rule I take from it is this: authors, testers, and reviewers should identify the assumptions an implementation relies on and try to construct an execution that breaks them. That obligation applies wherever AI enters the process.

Turning implementation assistance into an acceptable change

For my own development workflow, I would organize the work around four questions.

Which behaviors must the optimization preserve? For this read path, performance must be accompanied by an account of what data may be returned during replacement, file-size changes, and reclamation. Application code needs similarly specific requirements, such as whether a payment retry can charge twice or an old authorization remains usable after permissions change.

Do the tests exercise operations that could violate those requirements? A microbenchmark answers a throughput question. Correctness tests must also interleave reads with eviction, writes, and length changes, checking returned bytes. Each test should support a defined claim.

Can the tests detect a known broken implementation? Deliberately removing a protection in an isolated test can reveal whether the test fails as expected. Such controls help establish coverage, particularly for concurrent paths that can run for a long time without exposing an error.

Does review contribute new evidence? AI self-review can explain code, identify omissions, and propose counterexamples. Another reviewer may also use AI. The useful question is whether review introduces a different interleaving, challenges another assumption, or adds a test that distinguishes correct behavior from incorrect behavior. Repeated statements that code looks right provide limited support.

These are the practices I draw from the case. They take time, so implementation, testing, review, and regression work should all count toward the cost of AI-assisted development when deciding whether an optimization is ready to ship.

Make delivery responsibility explicit as tools improve

I want to use AI more extensively for implementation, explanation, and finding counterexamples, and to measure the performance opportunities it helps uncover.

When accepting a change, I still want an evidence chain that can withstand questions: which bottleneck disappeared, which behaviors must remain intact, which interleavings were tested, which review concerns were resolved, and which conditions affect deployment?

These patches provide a concrete example. The 23x microbenchmark deserves attention, as does the race identified by review. Considering both is what makes it possible to decide how the code should change next and when it can be delivered.
