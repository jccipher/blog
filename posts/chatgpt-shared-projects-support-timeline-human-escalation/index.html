1. Why this timeline is a separate post

Part 1 preserves the complete reproduction and investigation. It also reclassified the incident from a cross-client synchronization failure with an unknown root cause to a currently stated support boundary. That answer raised a second set of questions: why the limitation exists, whether a project can be converted, what happens to Codex and ChatGPT Work history, and how a team should structure its shared context.

Those questions produced an AI-assisted reply and, after a human-review request in the original case, another named response. This post records all three inbound messages. A name and the absence of an AI notice describe the email; they do not independently establish authorship or the review process.

Five evidence labels are used:

  • Reproduced: directly observed in the clients;
  • Support-stated: written in an OpenAI Support message, but not automatically a public product specification;
  • Publicly documented: directly supported by a current OpenAI help article;
  • Inference or interim practice: a practical design based on current boundaries, not an official migration commitment;
  • Pending human confirmation: stated by AI-assisted support without complete public documentation.

3. First Support response: the operating boundary

The first email included this short, sanitized excerpt:

“Shared projects are not supported in the new ChatGPT desktop app.”

It then recommended opening ChatGPT in a browser and using the same account and workspace to access the shared Project.

That reply answered where the Project should be accessed today. It did not explain why support was absent, provide a desktop roadmap, or classify the behavior as a defect in a particular client version. Part 1 therefore records “support boundary clarified,” not “bug confirmed” or “bug fixed.”

4. Second, AI-assisted response: content and limits

The second email began with this limitation:

“We don’t have public documentation that explains why Shared Projects aren’t supported...”

It ended with an explicit warning:

“This response was generated with AI support which can make mistakes.”

Within that boundary, its main recommendations can be summarized as follows:

  1. Create and share the Project on the web or mobile, then assign coworkers Chat or Edit access;
  2. Use Move to project or drag-and-drop for eligible existing ChatGPT chats;
  3. Start a new chat inside the shared Project when an existing chat is not eligible;
  4. Re-add project instructions and sources as needed;
  5. No public material documents preservation of local-folder associations, Codex projects, or Codex history through a “conversion”;
  6. Codex and ChatGPT histories are separate; Shared Projects use project-only memory, where ChatGPT Work is unavailable;
  7. No public rationale, roadmap, or timeframe was available.

These statements do not all have the same evidence quality. Some map directly to public documentation, some summarize it, and some are conservative inferences from missing migration documentation.

6. The response in the original case

The 21:25 reply on October 12 supplied the missing distinction between project types. Its key short excerpt was:

“A desktop-created local-only project cannot be directly converted or automatically migrated into a Shared Project through ChatGPT web.”

The remaining guidance can be summarized without publishing identifying information:

  • Local-only projects: create a web-accessible ChatGPT Project, manually transfer relevant content, and then share it;
  • Already cloud-synced ChatGPT Projects: open the existing Project on the web and use Share; “create a new web Project first” therefore does not apply to every desktop-created project;
  • Content that can be added manually: move eligible chats when the action is available, and add instructions, files, and sources to the destination;
  • State that does not transfer automatically: local-folder associations, local Codex state, and other desktop-only project state; Codex history remains separate from ChatGPT history;
  • Business collaboration: use a web-accessible Shared Project as the common workspace, assign Chat/Edit permissions, and organize separate chats by task or workstream;
  • External sources: GitHub or Google Drive access depends on connected-app permissions and workspace configuration; the email does not promise that every source can be attached directly or synced automatically;
  • Future availability: no public roadmap or timeframe was available to share, so Support could not confirm when desktop support would arrive.

The reply still did not explain the product rationale or individually confirm that projects must originate on the web or how Work history should migrate. It responded to a human-review request without explicitly stating human authorship or completion of that review. It is therefore labeled a named Support follow-up in the original case.

7. A practical collaboration architecture

The original case's follow-up supports choosing a path according to the existing project object.

Case A: the existing object is already a ChatGPT Project

If it opens on the web and its sharing pane offers Share, prefer sharing that existing Project from the web. This preserves the Project's existing chats, files, and instructions. Do not delete or recreate it merely because macOS navigation omits it.

Use a stable team member as owner and apply least privilege: Chat access for members who only need to use the shared context, and Edit access for those who must manage instructions, files, or invitations. A Business workspace should also confirm that admins have not disabled project creation or sharing.

Case B: the existing object is a local folder, Codex project, or local Work context

Support says local-only projects cannot be directly converted or automatically migrated. A new web Shared Project can serve as a collaboration context hub, with shared content transferred item by item:

  1. Create or select a Shared Project on the web;
  2. Invite members from the same Business workspace and assign explicit Chat/Edit roles;
  3. Move only ChatGPT chats that actually expose Move to project;
  4. Re-add necessary instructions, summaries, and sources after permission and privacy review;
  5. Keep the GitHub repository, branches, and pull requests as the source of truth for code; use the Shared Project for goals, decisions, links, and handoff summaries;
  6. Keep local-folder and Codex execution history in their original environments and do not call them migrated;
  7. Run Work tasks in a separate Work context while the current project-only-memory restriction applies, then return shareable artifacts and decision summaries to the collaboration hub.

Steps 5–7 are an interim architecture inferred from current boundaries, not an OpenAI-released migration feature.

Use separate chats for separate tasks in the same Shared Project. The public article describes branching rather than synchronous collaboration in one chat, so research, implementation, review, and handoff can each have a focused conversation while sources and decision summaries carry the common context.

Data and permission cautions

  • Shared Project members can see project chats, files, and the member list; review access and sanitize material before adding it;
  • The owner retains critical controls such as deleting the Project and removing members; avoid assigning sole ownership to a temporary collaborator;
  • Keep important source code and formal documents in systems with version history and permission auditing;
  • Do not confuse “authenticated OpenAI email” with “AI-generated content approved by a human.”

8. How the human-review request was made

The actual action was to click Reply on the first named Support email. The message sent at 15:25 did four things:

  1. State Please escalate this case to a human support specialist;
  2. Explain that a separate AI-assisted response arrived later;
  3. Ask a human to confirm each material claim in that response;
  4. Request that the original support record remain open or be reopened rather than closed based only on automation.

The original case received migration and collaboration guidance that evening. This shows continuity of the reply chain, but does not establish completion of a human handoff. A future post will cite this one and record new confirmations, unanswered questions, and actual migration results when further evidence is available.
