When a Shared ChatGPT Project Vanishes on macOS: A Postmortem and the Official Support Boundary

PUBLISHED 2026.10.12 9 MIN READ — VIEWS #ChatGPT#macOS#Shared Projects#Cross-Client Consistency#Incident Response

Same account, same workspace, same sharing permission: the web client could open and edit a shared Project, while the macOS app could not find it in the sidebar, the full Projects view, or Project search results.

Privacy note: This post does not disclose the real project name, collaborator identities, account details, workspace identifiers, chat content, or original screenshots. “Target project” refers only to the affected shared research Project. The client version, test date, permission type, and support status are retained because they are necessary for reproducibility.

Series navigation: This is Part 1 of the “ChatGPT Shared Projects Support Log.” Continue with Part 2: the support timeline, escalation, and migration guidance.

In one sentence:

The behavior now has an official support boundary: the new ChatGPT desktop app does not currently support Shared Projects, so they should be accessed on the web; this is not an official confirmation of a defect in a particular client release.

1. How the issue appeared

While using ChatGPT Projects for research work, I noticed that the web and macOS clients displayed different project lists.

The target Project had been created by another collaborator and shared with the current account as an invited member with edit access. On the web, it appeared normally and could be opened and edited. In the macOS app, it did not appear in the sidebar.

A missing sidebar item does not by itself prove a synchronization failure. The cause could be a collapsed section, ordering, caching, or a different display scope. The investigation therefore continued across account and workspace checks, search results, membership, and the full Projects view.

The web behavior matched expectations: the target Project appeared in the list, opened successfully, and allowed the actions granted by its edit permission.

The macOS app behaved differently:

  • the target Project was absent from the sidebar;
  • expanding and scrolling through the list did not reveal it;
  • it was also absent from the full Projects view;
  • search could find related chats from inside the Project;
  • the same search did not return the Project entity.

This distinction matters because “the project data exists,” “its chats are discoverable,” and “the Project is visible as a navigation object” are three separate questions.

3. Investigation

3.1 Account and workspace

The first check confirmed that the web and macOS clients used the same account and the same workspace. Because the web client could directly access the target Project, the issue could not be explained simply by the wrong sign-in or a workspace switch.

Only the conclusion that these values matched is retained here; no account or workspace identifier is published.

3.2 Search result types

The next step used the same project keywords in both clients.

Search and navigation behavior Web macOS app
Find related chats Success Success
Find the Project entity Success Not shown
Show the Project in Projects Normal Missing
Enter through the project list Normal Not possible through the list

This result alone does not prove that the Project data failed to synchronize. The two clients may use different index scopes or result presentation rules. It does establish an observable difference in how the shared Project can be discovered and navigated.

3.3 Sharing permission

The web sharing panel confirmed that:

  • another member owned the Project;
  • the current account was an invited member;
  • the current account had Can edit permission;
  • access was limited to invited members;
  • the current account could enter and use the Project in practice.

This excluded obvious explanations such as temporary link-only access or an expired membership. It did not rule out a macOS refresh or rendering problem involving shared-project membership.

3.4 The full Projects view

To avoid relying on the sidebar alone, I opened the macOS app’s full Projects view. Other projects appeared there, along with search and sorting controls, but the target Project remained absent.

The reproducible facts can therefore be reduced to five points:

  1. The web client could discover and access the shared Project.
  2. The macOS app could discover related chats from inside it.
  3. The macOS app did not return the corresponding Project entity.
  4. Both the sidebar and the full Projects view omitted the Project.
  5. Account, workspace, membership, and edit permission had been checked.

4. The original hypotheses and what the support reply changed

Before the formal response arrived, the evidence supported several candidate explanations:

  • Shared-project list refresh: the macOS app may not have refreshed the complete set of shared Projects available to the account.
  • Separate chat and Project indexes: discoverable chats do not guarantee that the Project entity is indexed or presented in the same result set.
  • Navigation-layer rendering: the Project may still exist and remain accessible while being omitted from desktop navigation.
  • Version-specific compatibility: the issue occurred on 26.930.61225, but one reproduction is not enough to show that this release introduced a regression.

These hypotheses document reasonable investigation paths at the time; they are not verified root causes.

OpenAI Support's later reply changes the classification. The Project remaining available on the web while lacking a corresponding shared-Project navigation entry in the macOS app is consistent with Support's stated boundary that the new desktop app does not support Shared Projects. The behavior should therefore no longer be described as a synchronization failure whose root cause is still pending, nor should one reproduction be used to attribute a software regression to version 26.930.61225; the product's internal reason remains unknown.

The reply does not explain the product rationale, such as the sharing-permission model, client architecture, or staged availability. It also does not say when Shared Projects might become available in a future desktop release. In short, the current support boundary is clear; the internal reason and future roadmap remain unknown.

5. OpenAI Support's formal response

After the investigation, I submitted a support request through the OpenAI Help Center. The report included:

  • a sanitized description of the problem and its impact;
  • the web and macOS environment difference;
  • the client version and release date;
  • repeatable checks;
  • the sharing-permission conclusion;
  • a comparison of project lists and search behavior;
  • confirmation that the account and workspace had already been checked.

Support first confirmed that the request had been escalated to a support specialist. In the early hours of October 12, 2026, Beijing time, OpenAI Support then provided a formal response with three operational points:

  • the new ChatGPT desktop app does not currently support Shared Projects;
  • a shared Project should be opened in a browser;
  • the user should sign in with the same account and select the same workspace.

This post does not disclose the case number, support representative, recipient account, or private email link. The interpretation boundary is equally important:

  • Confirmed: Support clarified the current product-support boundary and provided a web access path.
  • Not explained: Support did not say why Shared Projects are unavailable in the desktop app.
  • Not confirmed: The response did not classify the behavior as a software defect in a particular client version.
  • Not provided: There is no future support timeline, fixed release, or delivery commitment.

The latest status is therefore not “bug fixed.” It is “support boundary clarified, web workaround available, desktop capability still unavailable.”

OpenAI's public documentation describes ChatGPT Projects in the desktop app at a general level, but the relevant page does not explicitly promise desktop support for Shared Projects. This post therefore attributes the Shared Projects limitation specifically to the support reply; it does not extend that statement to ordinary Projects or every kind of desktop project.

6. Web workaround and follow-up checks

Until the supported surfaces change, collaborators can use this path directly:

  1. Open ChatGPT in a browser.
  2. Sign in with the same account used in the desktop app.
  3. Select the same workspace that owns the shared Project.
  4. Open the shared Project from the web Projects list.

If the Project is still missing on the web, continue with these checks:

  1. Confirm that both clients use the same account.
  2. Confirm that both clients are in the same workspace.
  3. Verify invited membership and permission on the web.
  4. Reopen the original invitation link and confirm that the current account joined successfully.
  5. Record the reproduction date, affected client, and minimal reproduction steps.
  6. If web access also fails, send OpenAI Support sanitized evidence.

Avoid deleting the Project, removing members, or recreating it merely to force a refresh. The missing desktop entry matches the support boundary described by Support, so those actions may not change the result and can increase collaboration and recovery costs.

7. Product implications

A shared Project has at least three distinct states:

  • Permission state: whether the account belongs to the Project and what it may do.
  • Content-access state: whether chats, files, and instructions remain usable.
  • Navigation-visibility state: whether the client shows the Project entity in lists and search.

These states do not substitute for one another. Finding chats from inside a Project does not prove that Project navigation works; a missing list item does not necessarily mean the underlying data is gone.

As Projects carry more long-running research and team collaboration, cross-client consistency becomes more than a UI detail. Clear shared-project status, visible refresh feedback, and consistent result types directly affect whether users can trust that their working context is complete.
