从 Linus 的 Claude Code 内核补丁看 AI 编程的审查责任

发布于 2026.10.15 8 分钟阅读 — 次浏览 #Claude Code#Linux#Code Review#Concurrency

读完 InfoQ 关于 Linus Torvalds 使用 Claude Code 优化 Linux 页面缓存的报道，我最关注的是这段完整的开发过程：AI 参与实现和测试，Linus 报告本机性能数据，维护者在公开审查中指出竞态，补丁继续修订。

这个过程同时展示了 AI 编程的价值和验证工作的难度。工具已经能够深入参与复杂系统的开发；一段跑得很快、经过测试和初步审查的代码，仍可能违反并发条件下的正确性要求。

我的判断是：采用 AI 编程之后，团队需要更明确地说明每项正确性主张由什么证据支持、由谁负责验收。

先看补丁做了什么

这次优化针对一个具体瓶颈：多个线程反复读取同一文件中的少量数据时，folio 的引用计数操作会形成争用。folio 可以先理解为内核管理文件缓存数据的内存单元。即使应用只读数据，取得和释放引用也要修改共享计数，让多个 CPU 争用同一条缓存行。Linus 的补丁说明：无 folio 引用的页面缓存读取

Linus 在说明中披露，Claude Code 在他的指导下参与了代码、测试程序、问题审查和说明初稿，测量在他的机器上完成。早期说明列出 8 个补丁；10 月 13 日公开讨论的 rcu-free-v3 则包含 10 个补丁。阅读这些结果时，需要保留版本区别。Linus 的补丁说明、Linus：Improve page refcount scalability

在后者的 Threadripper 微基准里，64 线程吞吐量从每秒 1330 万次读取升至 3.04 亿次，约为原来的 23 倍。Linus 同时明确指出：测试让所有 CPU 反复读取同一页的一小段区域，真实负载的收益会小得多。Linus：性能结果与测试条件

这个结果很好地暴露了共享计数对扩展性的限制。把它用于评估数据库、构建任务或线上服务时，还需要测量各自的工作负载。

RCU 保护了内存生命期 仍需检查文件状态

优化希望让常见读取路径省去 folio 引用计数操作，为此使用 RCU 延迟回收内存。RCU 的基本思路是把“从数据结构中移除对象”和“回收对象占用的内存”分开，等待已有读者离开相应临界区后，再进行回收。Linux 内核文档：What is RCU

这减少了读者的同步开销，也带来一个需要单独回答的问题：内存仍可访问时，它是否仍对应读取路径正在处理的文件状态？

Kiryl Shutsemau 在 filemap_read_rcu_batch() 中指出的竞态，正落在这里。下面按其邮件中的交错顺序简化展示：

顺序 读取线程 另一个线程
1 找到旧 folio A，并确认它仍在缓存槽位中
2 驱逐 A；RCU 暂缓回收其内存
3 写入数据，重新填充页面缓存并扩展文件长度
4 读取新的 i_size，却仍从旧 A 复制数据

读取线程把旧数据对象和更新后的文件长度组合使用，可能返回用户没有在相应位置写入的数据。这是文件读取语义的错误；“旧内存尚未回收”这一保证本身不足以排除它。Kiryl：竞态分析与双线程执行顺序

Linus 随后建议把 i_size 的读取提前，再统一检查缓存槽位是否仍指向该 folio。Kiryl 的修订进一步解释了标志位、内存屏障与检查顺序，并保留数据就绪状态检查。Linus：调整检查顺序、Kiryl：修订补丁与内存顺序说明

这段讨论体现了并发审查的价值：逐一说明对象在什么时候有效，以及几个分别有效的观察能否安全地组合使用。相同的问题也会出现在业务系统里，例如用旧权限判断批准新请求，或用旧库存快照执行新的扣减。

我怎样评价原文的结论

原文提醒读者保留人工代码审查，这一点我认同。维护者在公开审查中给出了具体反例，也推动了修订。

但“大神也没兜住”容易让注意力停留在个人失误上。复杂并发代码需要多人审查，恰恰因为作者的经验、测试结果和其他人的推理能够互相补充。在这次讨论中，Linus 提出调整方向，Kiryl 继续解释和修改；审查过程本身也是共同完成设计的过程。

同样，这个案例无法单独测出 AI 相对于人类的缺陷率。要比较两种开发方式，需要相近任务、相近测试投入、可比较的审查条件和足够多的样本。一次漏检能够说明当前证据没有覆盖某种交错，不能据此判断所有 AI 生成代码的可靠性。

我更愿意从中提出一个工作要求：作者、测试者和审查者都应主动寻找实现所依赖的假设，并尝试构造推翻它的执行过程。 无论其中哪一步使用了 AI，这个要求都成立。

把 AI 的实现能力转化为可验收的改进

如果把这件事带回自己的开发流程，我会围绕四个问题组织工作。

第一，优化必须保住哪些行为。 对这个读取路径来说，除了性能，还要说明并发替换、文件长度变化和回收期间允许返回什么数据。业务代码也需要这样的具体约束，例如支付重试是否会重复扣款、权限变化后旧授权能否继续使用。

第二，测试是否覆盖了会破坏这些行为的操作。 微基准回答吞吐量问题；正确性测试还需要安排读取与驱逐、写入、长度变化等操作交错，并检查返回的每个字节。二者应各自支持明确的结论。

第三，测试能否识别已知错误。 可以在隔离测试中故意移除一项保护，检查测试是否会失败。这样的反例有助于判断测试到底覆盖了什么，尤其适合那些正常运行很久也未必暴露问题的并发路径。

第四，审查是否带来了新的证据。 AI 自查可以帮助解释代码、列出遗漏和生成反例；另一名审查者也可以继续使用 AI。关键在于有没有提出不同的执行顺序、检查不同的假设，或增加能区分对错的测试。重复得到“看起来正确”的评价，支持力度有限。

这些是我从案例中提炼的实践建议。它们也会消耗时间，因此应该把实现、测试、审查和回归处理一起计入 AI 编程的成本，再判断一次优化是否值得交付。

交付责任需要随工具能力一起明确

我愿意在开发中更多使用 AI，让它参与实现、解释和寻找反例，也愿意把它帮助找到的性能机会认真测量出来。

接受改动时，我仍希望看到一条能追问下去的证据链：优化消除了什么瓶颈，哪些行为必须保持，测试覆盖了哪些交错，审查解决了哪些疑问，还有哪些条件影响部署。

Linus 的这组补丁提供了一个具体例子。23 倍的微基准结果值得研究，维护者给出的竞态反例同样值得研究。把这两种证据放在一起，才有条件判断代码下一步该怎么改、何时可以交付。
