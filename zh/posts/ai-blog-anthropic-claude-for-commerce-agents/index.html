Anthropic 把购物智能体、商家智能体、行业示例与 Claude Code 插件打包成一个快速起点。真正值得追问的不是演示能否迅速跑起来，而是它接入真实店铺后，哪些数据仍然权威、哪些操作可以复核、每条责任边界由谁掌握。

编辑摘要

Anthropic 此次发布的是商业智能体蓝图，而不是一个统一托管的购物产品。它提供消费者购物与商家运营两套可运行参考实现，覆盖零售、旅行、电信与票务场景。团队可以选择 Messages API、Agent SDK 或 Claude Managed Agents，也可以借助 Claude Code 插件把示例改造成符合自身目录、政策与品牌的版本。

这种产品形态本身就是核心判断。参考实现可以省去工具定义、编排、对话界面与常见护栏等重复脚手架，却不假设所有商家共享同一套后端。商品目录、结账、支付、订单历史、促销与运营政策仍连接企业既有系统。因此，这套蓝图更适合被理解为一份集成契约和一组默认做法，而不是商业基础设施的替代品。

两类智能体分别处理交易的两面。购物智能体留在零售商自己的应用或网站中，理解多商品需求，完成搜索与比较，记住偏好，在对话中展示商品和购物车，把购物车交给结账流程，并继续回答订单与售后问题。商家智能体位于店铺后台，回答销售问题、发现库存风险、建议定价或促销，并起草营销活动。

这种区分很实际，因为双方的权限边界并不相同。消费者智能体需要准确的商品、价格、库存、购物车与订单数据；商家智能体则可能接触更广的经营数据，并提出会产生财务后果的操作。Anthropic 表示，商家智能体主动建议的变更在上线前需要人工批准；购物参考实现则把商品与价格约束在目录数据内，并避免操纵式追加销售。这些控制比对话是否流畅更重要：如果系统会虚构库存或静默修改促销，再有说服力的回答也没有价值。

公告以采用情况和业务结果作为开场。Anthropic 称，使用 Claude 购物智能体的零售商曾观察到购物车金额最高增加 35%，完成购买的可能性最高增加 60%。文章还收录合作伙伴与客户关于搭建速度、部署体验和既有商业助手的说法。这些信息提供了方向性信号，但文章没有给出研究设计、样本量、基准、客户间分布，也没有说明最高增幅出现的具体条件。团队应把这些数字当作开展受控实验的理由，而不是对自身转化率的预测。

这次发布带来三条实施启示：

  1. 用蓝图暴露缺失的系统契约。 在连接模型前，明确价格、库存、资格、支付、退货和客户身份分别由哪个服务负责，并让工具 Schema 显式表达这些边界。
  2. 衡量整笔交易，而不只看一次调用。 有效试点应同时跟踪任务完成率、纠错与升级率、延迟、放弃率、利润、退货、政策违规和客户满意度，而不只看购物车金额或演示是否成功。
  3. 严格区分建议与承诺。 搜索和解释可以容纳模型判断；退款、折扣、营销活动与结账则需要确定性校验、适当审批、幂等机制和审计记录。

这套蓝图的价值，在于把一组生产模式与可运行示例压缩成便于采用的起点。真正的考验从第一个小时之后开始：接入混乱目录、解释模糊政策、处理局部失败、限制写操作权限，并证明智能体在不削弱信任的前提下改善了客户结果。代码仓库可以加速这些工作，却无法替团队作出相应的业务决策。

原文要点

Anthropic 宣布一套开放商业蓝图，其中包含购物智能体与商家智能体参考实现。公司表示，这些示例可以通过 Claude API、Amazon Bedrock、Microsoft Foundry 或 Google Cloud Vertex AI 部署，并提到 Accenture、Mastercard 与 Visa 等实施和生态合作伙伴。

购物参考实现连接商品搜索、多商品规划、个性化、购物车、结账交接、订单历史、客户服务以及对话内结构化界面。支付仍由商家既有结账系统或其选择的支付服务商处理。Anthropic 称，参考实现包含以目录数据约束商品与价格行为的护栏。

商家参考实现面向店铺运营人员，可以分析销售、标记库存问题、提出定价和促销建议并起草营销活动。文中描述的流程会在建议的变更发布前保留人工审批。

原文还收录多家商业与技术公司的说法，涉及信任、个性化、支付、部署速度和既有智能体项目。其中一些介绍了对蓝图的早期搭建体验，另一些解释了为何选择在 Claude 上构建商业助手。文章最后链接到公开代码仓库、各行业演示和一篇独立工程深度文章。

这是一篇产品发布公告，并未给出参考智能体的对比评测、转化率数据的详细方法、生产成本测量或适用于所有公司的部署模式。这些问题仍需每支团队结合自身数据、风险控制、系统和客户旅程验证。
