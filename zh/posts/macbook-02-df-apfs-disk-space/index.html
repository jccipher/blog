MacBook 使用心得与最佳实践 02：读懂 df -h 与 APFS 磁盘空间

发布于 2026.10.22 9 分钟阅读 — 次浏览 #MacBook#Terminal#APFS#Disk Space#df#du

💻 在 MacBook 终端里输入 df -h，本想看看硬盘还剩多少空间，结果看到一串 /dev/disk…：好几行容量都是 926Gi，可用空间都是 484Gi，还有两行赫然写着 100%。

这些数字并不矛盾。这份样例的主 APFS 容器约有 926Gi 容量，还剩 484Gi；重复出现的是共享空间的不同卷，两处特殊文件系统的 100% 也不表示硬盘已经写满。

这是 MacBook 使用心得与最佳实践系列的第 02 篇。本文以一份实际终端输出为例，解释 macOS 的磁盘统计。样例数值只代表当时状态；文档与本机命令手册核对日期为 2026 年 10 月 22 日。设备编号和辅助卷布局会因电脑与系统版本而变化。

一、先读命令：df -h 到底查什么？

df -h

df 查看已挂载文件系统的空间统计；不指定路径时，通常列出当前已挂载的各个文件系统。-h 表示以方便阅读的单位显示容量。macOS 的 df(1) 手册列出了参数和统计口径。[1]

终端中的这一行：

➜  ~ df -h

前面的 ➜ ~ 是命令提示符。~ 表示当前用户的主目录，真正执行的命令只有 df -h。

这里也要分清单位：

显示 含义
Ki 以 1,024 字节为一个单位，即 KiB
Mi 以 1,024² 字节为一个单位，即 MiB
Gi 以 1,024³ 字节为一个单位，即 GiB
Bi 字节

df -h 的容量列使用 1,024 进制，df -H 则使用 1,000 进制。硬盘厂商通常使用十进制 GB、TB；1GiB 约等于 1.074GB，两种写法不能直接当成相同数值比较。

日常关心用户文件和应用占用时，可以先找到 /System/Volumes/Data：

/dev/disk3s1  926Gi  416Gi  484Gi  47%  2.4M  5.1G  0%  /System/Volumes/Data
列名 含义 样例解读
Filesystem 文件系统或设备标识 /dev/disk3s1 标识一个卷，不能据此数物理硬盘
Size 报告的总容量 这里体现约 926Gi 的共享容器容量
Used 该卷已使用的空间 Data 卷约用了 416Gi
Avail 该文件系统可用的空间 此处为各卷共享的约 484Gi
Capacity 按该卷已用与可用空间计算的使用比例 47% 不等于整块硬盘的占用率
iused 已使用的 inode／文件节点数 2.4M 约为 240 万个节点
ifree 文件系统报告的可用节点数 5.1G 表示数量，不是 5.1GiB 容量
%iused 文件节点使用比例 0% 是取整后的显示，不代表没有文件
Mounted on 挂载点 通过哪个目录接入并访问该文件系统

inode 可以粗略理解为记录文件、目录等对象信息的节点，不必把它当成严格的“普通文件总数”。APFS 下也不宜用 ifree 直接推算还能创建多少个文件。日常判断磁盘余量，先看容量列。

挂载点（mount point）就是文件系统接入目录树的位置。 / 是整棵目录树的根；挂载在它下面的卷可以有自己的空间统计。因此，根目录这一行的 13Gi 并不是整台 Mac 所有数据的大小。

三、为什么好多行都是 926Gi？

关键在 APFS 容器（container）与卷（volume） 的区别。

同一个 APFS 容器可以包含多个卷。各卷按需使用空间，共享容器中的空闲部分；某个卷增长，会减少其他卷能使用的余量。Apple 的 APFS 宗卷说明介绍了这一机制。[2]

这份样例可以画成：

主 APFS 容器：约 926Gi
├─ Data       已用约 416Gi
├─ 系统卷     已用约  13Gi
├─ Preboot    已用约  10Gi
├─ VM         已用约   2Gi
├─ Recovery、Update 与其他开销
└─ 各卷共享的剩余空间：约 484Gi

因此，多个 926Gi 不能相加，重复的 484Gi 也只能算一次。926Gi - 416Gi 不等于 484Gi，是因为 Data 之外的卷及文件系统开销也使用了容器空间。

如果只用这份经过舍入的输出粗算，主容器已占用约：

926Gi - 484Gi ≈ 442Gi
442 ÷ 926 ≈ 48%

这是主容器层面的近似值，不是整块物理 SSD 所有分区的精确统计。需要更完整的容器信息时，用 diskutil apfs list。

四、Capacity 为什么显示 47%，而不是 45% 或 48%？

在这种共享空间的输出里，macOS df 的口径是：[1]

Capacity = 该卷已用空间 ÷（该卷已用空间 + 该卷可用空间）

数据卷近似为：

416 ÷（416 + 484）≈ 46.2%

df 通常将百分比向上取整，而容量列本身也经过舍入，因此这里显示 47%。不要拿显示出来的整数容量精确反推底层统计。

三种比例回答的是不同问题：

算法 回答的问题
416 ÷ 926 ≈ 45% Data 卷占容器总容量的大约多少
416 ÷ (416 + 484)，显示 47% df 对 Data 卷采用的使用率口径
(926 - 484) ÷ 926 ≈ 48% 主容器整体大约用了多少

判断还能继续写入多少数据，优先看 Avail，再结合容器统计；不要把某一行的 Capacity 当成整个 SSD 的统一占用率。

五、这些系统卷都在做什么？

系统和用户数据分开存放，是现代 macOS 的正常设计。Apple 平台安全指南中的 APFS 说明解释了核心卷的职责，以及 macOS 11 及后续版本从系统快照启动的方式。[3]

挂载点或名称 可以怎样理解
/ 系统根目录；样例中的 disk3s3s1 对应挂载的系统快照
/System/Volumes/Data 可变数据，包括用户文件、用户安装的应用及许多系统运行数据
/System/Volumes/VM 存放虚拟内存交换文件；这里统计的是磁盘占用，不是内存条容量
/System/Volumes/Preboot 保存启动所需的辅助数据
/System/Volumes/Update 系统更新相关卷
/Volumes/Recovery 恢复系统卷
xarts、iSCPreboot、Hardware 系统内部的辅助卷，涉及启动、安全或硬件支持；具体职责不能只凭 df 完整判断
/System/Volumes/Update/SFR/mnt1 更新目录下的辅助挂载；仅凭这一行不能确定来源，更不能断言它是另一块物理硬盘

设备编号是标识，不是产品清单。比如 disk3 可以表示一个合成的 APFS 容器；s1 等后缀用于区分其中的卷或其他切片。要核对层级和设备来源，应查看 diskutil list 和 diskutil info。

六、devfs 和 auto_home 的 100% 要处理吗？

devfs          ... 100% ... /dev
map auto_home  ... 100% ... /System/Volumes/Data/home

devfs 是用于呈现设备节点的虚拟文件系统。map auto_home 是自动挂载服务的映射入口。它们并不是普通的文件存储卷，容量数字不能照搬普通磁盘的判断方式。

在这份输出中，这两处 100% 本身不构成磁盘空间不足的证据。 真正需要关注的是承载文件的存储卷及其容器，而这里主容器仍有约 484Gi 可用。

七、从“还剩多少”查到“谁占用了空间”

df 和 du 可以配合使用：df 看文件系统余量，du 看指定文件或目录的占用。 以下命令用于查看信息。

1. 只看主目录所在文件系统

df -h ~

这里查的是“承载主目录的文件系统”，不是“主目录自己有多大”。想隐藏文件节点统计，可以加大写的 -I：

df -h -I ~

2. 看主目录以及各一级目录的大小

du -sh ~
du -h -d 1 ~ | sort -h

第一条汇总主目录占用；第二条显示一级目录，并按可读容量从小到大排序，底部还会包含主目录总计。-d 1 限制输出层级，扫描仍需读取其下层内容，目录大时可能耗时。

若出现 Operation not permitted 或 Permission denied，表示有目录未能读取，结果可能不完整。du 遍历得到的目录占用，也不能直接等同于 APFS 容器总用量；扫描范围、访问权限、快照和共享数据块等都会影响比较。

3. 看物理磁盘、容器和卷的关系

diskutil list
diskutil apfs list

需要调查样例中的最后一个挂载时，可以进一步查看：

diskutil info /dev/disk2s1

这条设备路径只对应本例。换一台电脑，或挂载状态发生变化后，应先用 diskutil list 找到当前标识。

4. 查本机命令手册

man df
man du
man diskutil

按 q 退出手册。macOS 自带命令与 Linux 常见的 GNU 版本可能使用不同参数，复制命令前，以本机手册为准。

八、一张日常速查表

想知道什么 使用命令
所有已挂载文件系统的空间 df -h
主目录所在文件系统还剩多少 df -h -I ~
主目录自己占用了多少 du -sh ~
主目录下哪些目录较大 du -h -d 1 ~ | sort -h
磁盘与分区、容器的关系 diskutil list
APFS 容器的空间分配 diskutil apfs list

再看到类似输出时，可以先找 Data 行的 Avail，再确认 APFS 容器结构，最后用 du 追踪具体目录。这比逐行相加容量，或只盯住一个 100%，更容易得到准确判断。
