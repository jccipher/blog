AI 工作空间错位复盘：Captain Noodle 的笔记为何掉进了 Disco Potato？

发布于 2026.10.10 10 分钟阅读 — 次浏览 #AI Agents#ChatGPT#Codex#Workspace Isolation#Incident Response

我的项目叫 Captain Noodle，助手却把笔记保存到了 Disco Potato。项目没有改名，真正错位的是聊天归属与本地执行目录；更危险的是，助手把执行上下文当成了用户意图。

脱敏说明： 项目名、聊天名和笔记文件名均为虚构代称，不代表实际改名。设备细节已泛化，事件日期与时间以相对顺序呈现；事实关系与调查结论保持不变。页面显示的是文章发布日期，不是事件发生时间。

TL;DR

维度 结论
故障表现 Captain Noodle 项目的笔记被保存到另一个已有项目 Disco Potato 的目录
已确认机制 最早的相关聊天创建时已带有旧目录；两次分叉后目录仍保持相同
放大因素 助手把执行目录误当成项目身份，引入不相关背景，并在写文件前未确认目的地
尚未查明 客户端最初为什么选择了那个目录，以及聊天项目归属变化的完整历史
不支持的结论 不能据此认定项目被改名、被转换为 Work，或用户手动设置过目录
核心改进 将项目归属、执行方式、执行目录与本次写入目的地分别核验

一句话总结：

能够在某个目录写文件，不等于用户希望把这次内容写在那里。

1. 一份笔记，暴露了两个项目之间的错位

我创建了名为 Captain Noodle 的 ChatGPT 项目，准备把闲置电脑整合成家庭开发与服务环境。

为了让讨论各自聚焦，我使用了几个聊天：Sock Drawer、Deploy-o-Saurus 和 Hamster Gym。讨论过程中，我让助手将一段笔记保存为 snack_notes.md，并要求以后持续追加。

助手报告文件已经保存，但给出的链接指向另一个已有项目：Disco Potato。

于是问题出现了：

我的项目明明是 Captain Noodle，为什么笔记跑进了 Disco Potato？

我进一步说明：这是 ChatGPT 项目，我没有为它设置那个本地目录，也找不到助手所说的目录设置入口。

调查不能停在“目录不一样”这个表面现象上。需要分别回答：

  1. 当前聊天在应用里属于哪个项目？
  2. 本地执行器实际使用哪个目录？
  3. 这个目录是在什么时候进入聊天上下文的？
  4. 有哪些证据能解释最初的选择，哪些还不能？

2. 项目没有改名：三个身份不能合并理解

重新核对应用项目列表与聊天执行记录，得到以下关系：

对象 记录中的身份 文件访问情况
Captain Noodle ChatGPT 项目 返回的项目记录没有本地目录字段
Disco Potato 独立的本地项目 对应另一个已有目录
Hamster Gym 聊天 归入 Captain Noodle 的本地 Codex 执行线程 执行目录仍指向 Disco Potato

这里必须区分三个概念：

  • 项目归属：聊天在应用中被归入哪个项目。
  • 执行方式：聊天由什么执行器运行，是否具备本地工具。
  • 执行目录：这些工具实际在哪个目录读取和写入文件。

“聊天属于 Captain Noodle”，不能推出“它的本地执行目录就是 Captain Noodle”。“聊天具备本地工具”，也不能证明用户把项目转换成了 Work。

OpenAI 官方文档区分了 ChatGPT 项目的共享来源与本地项目的文件夹访问，并说明聊天会保留记录的工作目录。这有助于理解概念，但不能单凭文档解释这次异常的具体触发原因。项目与聊天官方说明

3. 调查方法：从当前状态追溯到创建记录

当前状态可以证明错位，却不能单独解释错位如何形成。调查继续检查本地会话创建记录、只读数据库和桌面客户端日志。

检查时采用两个原则：

  • 交叉核验：会话元数据与客户端请求日志是否指向同一条创建或分叉事件？
  • 按时间回溯：错误目录是在保存笔记时出现，还是更早就已存在？

聊天代称只用于区分会话，并不代表它们创建时就使用了这些名称。

顺序 发生的事件 记录能够证明什么
第一天，首次创建 创建 Sock Drawer 聊天 创建记录已经带有 Disco Potato 目录；客户端使用本地执行环境
第一天，稍后 分叉出 Deploy-o-Saurus 分叉来源字段确认父聊天，目录保持相同
第二天 再次分叉出 Hamster Gym 父聊天关系再次确认，目录仍保持相同
随后 助手回答跨聊天访问问题 把执行目录名称误当成项目身份
再随后 按要求保存笔记 文件与持续追加规则写入另一个项目目录
用户指出问题后 核对项目归属与执行记录 确认目录关联早于笔记写入，并在两次分叉后保留

因此，可以排除一个解释：

不是保存笔记的动作，才让聊天关联到另一个项目目录。

更早的聊天创建时就已携带那个目录，后续分叉继续保留它。

4. 已确认的传播链，以及助手的责任

这个过程有两个不同层面。

4.1 项目归属与执行目录发生错位

当前项目归属与本地会话目录指向不同对象，这是有直接证据的事实。

但调查没有找到完整的项目归属变化历史。因此，不能断言聊天是先创建后移入项目，也不能断言它直接从该项目中创建。传播图描述的是已观察到的关系，不是对缺失界面操作的补写。

4.2 助手没有识别错位，反而扩大了影响

助手将目录名称当作项目名称，并引入另一个项目的背景。用户要求保存文件时，助手又默认当前执行目录就是正确位置。

这不是一句“执行环境提供了错误目录”就能免除的责任。

执行环境告诉助手可以在哪里操作；用户请求告诉助手应该完成什么目标。两者之间仍需要目的地校验。

把执行上下文解释成用户意图，是助手的判断错误。

5. 根因边界：传播机制明确，初始触发条件仍然开放

最早的创建记录显示：客户端以本地执行方式创建了聊天，并使用了 Disco Potato 目录。

但现有日志没有记录那次界面操作的完整过程，也没有保留足以追溯最初目录选择的完整参数链。

候选解释 证据边界
客户端沿用了此前的目录或输入框状态 缺少创建时状态，不能用当前状态反推
创建入口或项目归属处理存在客户端缺陷 缺少完整选择链路和受控复现
用户曾在某个入口选择过目录 用户表示没有设置；日志也不能证明其选择过
聊天后来被归入项目，但保留原目录 可以解释现象，但没有找到此次归属变化的时间记录

这里最容易发生两次推断越界：

  • 把“客户端提交了这个目录”改写成“用户设置了这个目录”。
  • 把“观察到状态错位”改写成“已证实某个确定的产品缺陷”。

两者都超出了现有证据。

要进一步定位，需要创建时的目录选择参数、当时的界面状态，或在隔离目录中进行受控复现。向产品支持提交反馈时，也应提供脱敏后的关键字段，而非完整本地日志。

目前查清的是传播机制；最初目录选择的触发条件仍未完全查明。

6. 实际影响，与不能推出的结论

已确认的影响包括：

  • 当前讨论被引入另一个项目的背景。
  • snack_notes.md 被保存到另一个项目目录。
  • 持续追加笔记的规则被写入那个项目的工作区规则。
  • 相关讨论也进入了那个项目的对话记录。

这不等于项目被改名，也不能证明项目被转换为 Work，或存在跨账号权限突破。

在事件调查阶段，没有修改应用数据库、重绑定聊天目录、迁移或删除已有笔记；也没有进行 GitHub 提交、推送或发布。该阶段只做与事件有关的只读检查，并生成审阅材料。

发现错位与修复错位，必须分开记录。 下面的防范建议不代表修复已经实施。

7. 防范清单：不要让笔记再次迷路

写文件前，核对项目、目录与目的地

在保存项目文件之前，分别确认：

  1. 用户所指的项目与目标。
  2. 当前执行器的工作目录。
  3. 本次文件应该保存的位置。

三者不一致时，先明确位置，不能仅凭目录名猜测。

分叉聊天，不只检查话题

分叉可以保留历史，也可能保留原有执行上下文。聊天名称与项目归属看起来正确，不代表执行目录也已经正确。

纯讨论可以先提供聊天内可审阅的 Markdown；需要本地文件时，再确认目的地。

将权限检查与意图检查分开

沙箱允许访问某个目录，解决的是权限问题；用户是否希望本次内容写入那里，解决的是意图问题。

权限校验不能代替项目身份和写入目的地校验。

为未知保留位置

可信的复盘应该同时说明：

  • 已证实的事实。
  • 有依据的解释。
  • 仍待验证的假设。
  • 继续调查需要什么证据。

“尚未完全查明”不是复盘失败。把未知包装成已知，才会制造下一次错误。

8. 结语：面条船长没有变成迪斯科土豆

Captain Noodle 没有变成 Disco Potato。

真正发生的是：聊天归属、执行方式与本地工作目录出现错位。旧目录在最早的相关聊天创建时就已存在，经过两次分叉继续保留；助手随后把执行上下文误当成用户意图，导致笔记落到错误位置。

最初为什么选中那个目录，仍然需要更多证据。

对于能够读写文件的 AI 助手，正确回答问题只是第一步。它还必须确认：

自己正在替哪个项目工作，又将把结果写到哪里。

来源与证据边界

  • 本文基于一次真实事件的一手调查记录，已进行脱敏。原始会话标识、日志、个人路径与真实名称不公开。
  • OpenAI：Projects and chats 用于解释项目与目录的概念，不作为此次初始触发条件已经确定的证据。
  • 本文报告单次事件的已确认机制与调查限制，不声称该现象适用于所有项目、聊天或客户端版本。
