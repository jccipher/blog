商业智能体如何进入生产：架构、延迟、安全与评测

生产级商业智能体不是“模型加一段购物提示词”，而是一条受控循环：Skills 承载流程，工具保留业务系统的权威性，界面展示真实状态，harness 决定哪些操作最终可以发生。

编辑摘要

Anthropic 这篇商业智能体指南的价值，在于它把模型还原成生产系统中的一个组件。推荐架构的中心很简洁：一个高能力模型运行 agent loop，通过 Skills 学习不常使用的领域流程，并调用由现有权威系统支撑的类型化工具。记忆、策略执行和评测围绕这个循环建设，而不是被当成提示词优化的附属问题。

文章倾向单一主智能体，核心原因是上下文。一次商业会话可能连续经过商品发现、比较、替换、客服、购物车修改和结账，各领域没有干净的分界线。如果每一步都路由给不同子智能体，购物车、偏好、屏幕状态和对话历史就要反复经过有损交接。Anthropic 建议把高频行为放进系统提示词，把长尾流程放进按需加载的 Skills。只有独立研究任务，或已经拥有完整合规与用户关系的专用领域，才更适合单独智能体。

这套架构也明确区分模型判断与业务逻辑。搜索、排序、库存、促销、分析和支付规则继续由企业已有服务掌握。智能体工具调用这些服务，只返回下一步推理所需的字段。模型可以判断怎样组合与展示权威结果，但不应重写企业的排序算法，也不应制造第二份事实来源。

界面本身也是协议。商品卡片、行程表、座位图和对比表被建模为类型化展示工具，而不是要求模型在文本中生成自定义标签。服务端可以校验结构，对话中也会留下实际布局的机器可读记录。用户下一轮说“第三个方案”时，智能体能够根据已经渲染的内容解析指代。

整篇文章最重要的生产原则是：模型提出方案，确定性代码决定执行。付款、退款、改价和营销活动先进入暂存状态，经过人或策略批准才真正生效。写操作只接受服务器签发的 ID，额度针对执行后的最终状态检查，必要时串行化并发写入，第三方文本在进入上下文前经过清洗。即使提示词被误解或遭遇注入，这些边界仍能继续工作。

由此可以提炼出三个实施重点：

  1. 优化完整任务，而不是孤立调用。 模型轮次、后端工具速度、独立调用并行、渐进式渲染和 Prompt Cache 必须与任务质量及尾延迟一起评估。
  2. 把记忆当作受治理的数据。 需要跨 Session 保留的事实应进入可查询的数据系统，并具备写入校验、权限、纠错、删除和保留期限，而不是只留在模型上下文里。
  3. 评测可到达的状态与最终结果。 直接重建困难的会话快照，覆盖正反案例与跨能力组合，检查最终状态和界面输出，而不是要求模型走唯一的推理路径。

我的主要结论是“架构耐久性”。更强模型可以作为一次配置升级，再经过评测扫描进入系统；与此同时，业务工具、安全规则、记忆存储、审批界面和测试案例继续定义产品。这比每次升级模型都重新设计外围系统可靠得多。

原文要点

原文基于零售、市场平台、旅游、娱乐和电信领域的商业智能体部署经验，将问题分成三个层次：确定架构、降低真实与感知延迟及成本，以及在生产环境中处理记忆、安全和评测。Anthropic 还提供了参考实现，包含面向消费者与商家的多个商业场景样例。

对于指令组织，文章提出按频率划分：大多数会话都需要的行为放进系统提示词，不常见的流程放进按需加载的 Skills。安全、法律、品牌和关键用户约束无论频率如何，都应留在系统提示词中。若页面入口等信号已经能预测所需 Skill，harness 可以在首轮调用前直接注入。

工具应建立在成熟后端逻辑之上，并将结果整理成适合模型推理的形态。错误响应最好给出下一步纠正方式，而不只是返回模糊错误码。展示工具能够保存结构化界面状态，但团队需要在服务端 Schema 校验与更细颗粒度流式输出之间做出选择。

性能部分把任务总延迟视为所有模型轮次与工具处理时间之和。建议包括：提前加载高概率相关上下文、并行调用独立工具、参数生成完成后立即执行、流式展示可见进度，以及用稳定前缀组织上下文以提高缓存命中率。模型大小和推理强度要经过真实评测选择，并按每个成功任务的成本衡量。

生产部分覆盖受治理的记忆存储、异步事实提取、分层读取、确定性交易控制、服务器签发 ID、最终状态额度检查，以及第三方商业内容清洗。评测策略强调可复现快照、复杂前置状态、负向案例、界面行为、跨能力组合、真实事故和领域专家参与。多团队协作时，每个工具和 Skill 都要有明确 Owner，改动携带目标测试，定期运行全量套件，并用灰度发布和独立开关控制风险。

这些结论来自 Anthropic 的商业实践，并非对所有系统都自动成立。团队仍需根据自己的流量结构、风险模型、成本约束和用户体验进行验证。
