1. 为什么单独记录这条时间线

第 1 篇已经保留了完整复现与排查过程，并把问题定性从“待查明根因的跨端同步故障”修正为“客服所述的当前支持边界”。但随后产生了新的问题：为什么不支持、能否转换项目、Codex 与 ChatGPT Work 的历史如何处理、多人协作应该以什么作为共享上下文。

这些问题触发了第二轮 AI-assisted 答复，以及回到原工单请求人工处理后的具名回复。本文按实际收发件记录呈现三封回复；“具名、没有 AI 声明”只描述邮件外观，不单独证明作者身份或人工审阅流程。

本文采用五级证据标签：

  • 已复现： 可以由实际客户端行为直接验证；
  • 客服所述： 来自 OpenAI Support 邮件，但不自动等同于公开产品规范；
  • 公开文档确认： 可以在 OpenAI 当前帮助文档中找到直接对应；
  • 推断或临时建议： 基于现有边界形成的操作方案，不代表官方迁移承诺；
  • 等待人工确认： AI-assisted 邮件提出、但公开文档没有完整覆盖的内容。

3. 第一轮 Support 回复：支持边界

第一轮邮件的脱敏短引文如下：

“Shared projects are not supported in the new ChatGPT desktop app.”

邮件随后建议从浏览器打开 ChatGPT，并使用相同账号和工作区访问共享 Project。

这封回复解决的是“现在应从哪里访问”，没有解释“不支持的原因”，也没有提供桌面端路线图。它还没有把现象认定为某个客户端版本的程序缺陷。因此，第 1 篇将最新状态写成“支持边界已澄清”，而不是“Bug 已确认”或“Bug 已修复”。

4. 第二轮 AI-assisted 回复：主要内容与限制

第二轮邮件在开头明确表示：

“We don’t have public documentation that explains why Shared Projects aren’t supported...”

邮件末尾同时声明：

“This response was generated with AI support which can make mistakes.”

在这一限制下，邮件给出的主要建议可以脱敏归纳为：

  1. 在 Web 或移动端创建并共享 Project，再给同一 Business 工作区的成员分配 Chat 或 Edit 权限；
  2. 使用 Move to project 或拖放，把符合条件的现有 ChatGPT 聊天移入项目；
  3. 无法移动的聊天应在共享 Project 中重新开始；
  4. 根据需要重新添加项目指令和来源；
  5. 没有公开资料说明本地文件夹关联、Codex 项目或 Codex 历史能够通过“转换”保留；
  6. Codex 与 ChatGPT 历史分开；Shared Projects 自动使用 project-only memory，而该内存模式下 ChatGPT Work 不可用；
  7. 没有可提供的公开产品原因、路线图或时间表。

这些内容不是同一种证据。有些可以由公开文档直接确认，有些只是 AI 对文档的总结，还有些是它根据“没有文档”作出的保守推断。

6. 回到原工单后的 Support 答复

10 月 12 日 21:25 的新回复给出了此前缺失的项目分类。邮件中最关键的一句是：

“A desktop-created local-only project cannot be directly converted or automatically migrated into a Shared Project through ChatGPT web.”

中文意译：桌面端创建的本地专属项目，不能通过 ChatGPT Web 直接转换或自动迁移为 Shared Project。

其余主要内容脱敏归纳如下：

  • 本地专属项目： 创建一个 Web 可访问的 ChatGPT Project，手工转移必要内容，再进行共享；
  • 已经云端同步的 ChatGPT Project： 在 Web 打开原项目，直接使用 Share；因此不能把“必须新建 Web 项目”泛化到所有桌面创建的项目；
  • 可手工带入的内容： 在界面提供该选项时移动合格聊天，并向目标项目添加指令、文件与来源；
  • 不会自动带入的状态： 本地文件夹关联、本地 Codex 状态或其他桌面专属项目状态；Codex 历史继续独立于 ChatGPT 历史；
  • Business 协作： 将 Web 可访问的 Shared Project 作为共同协作空间，分配 Chat/Edit 权限，并按任务或工作流组织独立聊天；
  • 外部来源： GitHub、Google Drive 等来源能否访问，取决于连接应用权限与工作区配置；邮件没有承诺所有来源都可直接添加或自动同步；
  • 未来支持： 当前没有可分享的公开路线图或时间表，不能确认桌面能力何时可用。

这封回复没有说明桌面端不支持的具体原因，也没有逐项确认“项目必须先在 Web 创建”或 Work 历史如何迁移。它回应了转人工请求，但没有明确声明答复由人工撰写或 AI 回复已完成人工复核。因此，本文将其标注为原工单具名 Support 后续答复。

7. 当前可执行的协作方案

根据原工单的后续答复，可以按以下两种对象选择路径。

情形 A：现有对象本来就是 ChatGPT Project

如果它能在 Web 打开，并且共享面板提供 Share，优先直接从 Web 共享现有 Project。这样可以保留该 Project 已有的聊天、文件和项目指令；不要仅因为 macOS App 看不见就先删除或重建。

建议由稳定的团队成员担任 owner，按最小权限分配：只需要使用上下文的成员给 Chat 权限，需要维护指令、文件或成员的人员再给 Edit 权限。Business 工作区还应先确认管理员没有禁用项目创建或共享。

情形 B：现有对象是本地文件夹、Codex 项目或本地 Work 上下文

客服已说明本地专属项目不能直接转换或自动迁移。可把新的 Web Shared Project 作为协作上下文中心，逐项手工带入共享内容：

  1. 在 Web 创建或选定一个 Shared Project；
  2. 邀请同一 Business 工作区成员，并明确 Chat/Edit 权限；
  3. 只移动明确显示 Move to project 的 ChatGPT 聊天；
  4. 经过脱敏与权限检查后，重新添加必要的项目指令、摘要和来源；
  5. GitHub 仓库、分支与 PR 继续作为代码事实来源；共享 Project 保存目标、决策、链接和交接摘要；
  6. 本地文件夹与 Codex 执行历史仍保留在各自环境，不把它们当作已迁移；
  7. 需要 Work 的任务继续在独立的 Work 上下文中运行，因为 Shared Project 的 project-only memory 与 Work 存在当前限制；完成后把可共享产物和决策摘要带回协作中心。

第 5 至 7 步是基于当前产品边界形成的临时架构，不是 OpenAI 已发布的迁移功能。

同一 Shared Project 中的聊天宜按任务拆分。公开文档说明成员可以分支聊天，而不是在同一聊天中同步协作；因此可分别安排研究、实施、审阅与交接聊天，用来源与决策摘要维持共同上下文。

数据与权限注意事项

  • 共享 Project 成员可以看到项目中的聊天、文件和成员列表；添加前先做访问范围与脱敏检查；
  • 项目 owner 保留删除项目、移除成员等关键能力；不要把唯一所有权交给临时成员；
  • 重要源码与正式文档应继续保留在有版本控制和权限审计的系统中；
  • 不要把“邮件来自 OpenAI 域名”误解为“AI 生成内容已由人工核准”。

8. 这次如何请求转人工

这次采取的是在第一轮具名回复的原始邮件中直接点击“回复”。15:25 发出的回信包含四个动作：

  1. 明确写出 Please escalate this case to a human support specialist；
  2. 说明后来收到一封单独记录下的 AI-assisted 回复；
  3. 要求人工逐项确认 AI 回复中的关键说法；
  4. 明确请求保留或重新打开原始处理记录，不要仅凭自动回复关闭问题。

结果是原工单当晚收到迁移与协作答复。这个过程证明回复关系得到保留，尚不足以证明后台已完成转人工。下一篇如有新证据，会引用本文并记录新增确认、仍未回答的问题与实际迁移结果。
