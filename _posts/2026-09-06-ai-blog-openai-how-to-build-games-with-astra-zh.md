> OpenAI 的游戏构建案例重点不只是要求 Astra 写更多代码，而是让一个模拟世界变得可观察：可重复场景、公开状态、浏览器测试、视觉检查点和性能计数器，让智能体能够调查“可以运行”和“体验正确”之间的距离。

## 编辑摘要

Thomas Ricouard 的 Void Explorer 从一项体验级要求开始：每颗可见恒星都应当可以抵达，玩家还应该从星际空间连续飞到行星表面。Astra 把这个方向实现为一款浏览器游戏，其中包含 2,048 个恒星系统和超过 10,000 颗程序化生成行星。规模很吸引人，但文章更耐久的启示，是项目如何同时建立多层反馈。

Ricouard 先定义体验和视觉方向，没有提前规定具体实现。生成式概念图确定色彩，并为轨道飞行、高速航行、进入大气层和着陆提供明确视觉目标。Astra 随后提出使用 TypeScript、Vite 和 Three.js 的应用架构，之后又把渲染层从 WebGL2 迁移到 Three.js 的 WebGPU 架构，同时保留既有模拟、导航和地形系统。

关键步骤是让 Astra 能够检查正在运行的游戏。Void Explorer 暴露一个小型 JavaScript 接口，提供当前天体、飞行模式、地形就绪状态、相机状态、Draw Call、三角形数量、地形任务队列和缓冲数据。命名测试场景为轨道、下降和着陆提供可重复起点。Playwright 可以载入场景、等待地形就绪、截图，并读取底层状态。另一些 Journey Test 仍会操作真实控制器，避免把预设场景误当成过渡过程已经正确的证据。

这是一种重要的智能体设计模式。“行星几乎消失了”这样的自然语言反馈很有用，但仍不够明确。可重现场景、截图、流式加载计数器和状态轨迹，可以把它变成调查任务。Astra 能够把视觉症状关联到速度曲线、地形调度、LOD 交接、几何体生成或渲染策略，修改实现，再执行同一项检查。人仍负责判断画面和控制手感是否达到要求。

多尺度世界让这些观察工具不可缺少。以光年计的距离和站在飞船旁边的人无法直接共享一套朴素坐标，否则近距离精度会丢失。模拟把大尺度物理地址与小范围局部偏移分开，并以保持在原点附近的观察者为参照渲染。行星最初只是由 Seed 决定的描述，只在需要的区域生成更多几何体。远距离 Proxy Sphere、Cube-Sphere Quadtree、局部地形块、碰撞表面、大气与云层必须在不同时间就绪，同时仍表达同一个世界。

文章给出了少见的具体测量案例。根据屏幕占比调整远距离行星精度后，一项受控对比中的 Proxy 几何体从 51,200 个三角形降到 7,040 个。索引化地形保持 241,952 个三角形不变，同时把传输缓冲从约 35 MB 降到 15 MB。新的细分策略在固定延迟模拟中把被丢弃的地形调度任务从 6,074 个降到 13 个。这些结果分别隔离几何体分配、数据传输和调度浪费；文章也正确地没有把它们包装成终端用户帧率基准。

这套工作流同时连接手工资产与程序化系统。Astra 把获批的飞船概念图转为 Blender 模型和运行时资产，而行星、地形、云、环和恒星仍由代码生成。另两款游戏探索了程序化水体：Sunwake 让同一波浪模型同时驱动画面和船只浮力；Hollowflux 则让水响应角色移动并传导攻击效果。在这些项目里，模拟系统不是装饰，而是由视觉和玩法共同使用。

其中有四种实践模式值得复用：

1. **先描述体验，再守住约束。** 视觉参考与交互目标提供稳定方向，即使底层实现发生变化也不会丢失目标。
2. **主动暴露状态。** 对智能体而言，一个小型调试接口往往比再增加一段问题描述更有价值。
3. **把预设场景与真实旅程结合。** 确定性检查点可以加速诊断，端到端控制流程则验证玩家确实能够抵达那里。
4. **测量真正发生变化的子系统。** 几何体数量、传输字节、废弃任务、帧间隔和截图分别回答不同问题，不能互相替代。

原文是一篇第一人称项目记录，不是智能体辅助开发与传统开发之间的受控对比。它没有公布总开发时间、Token 或算力成本、人工介入频率，以及多少代码后来需要返工。无头 Chromium 测量使用 SwiftShader 软件渲染，不代表 Ricouard 本地 GPU 的表现。行星地形采用 Heightfield，因此不支持洞穴、悬挑和可破坏隧道。这些限制不影响工程模式本身，却约束了对生产率或普遍游戏质量的外推。

我的主要结论是，当软件资产能够解释自身状态时，智能体开发才会显著改善。仅有一个可玩的浏览器页面仍然含糊，仅有测试套件也无法判断手感。项目通过暴露世界状态、固定起始条件、收集测量数据，并保留人工试玩，让 Astra 获得足够证据去独立行动，同时没有假装审美判断已经自动化。

#### 原文要点

文章记录了在 Codex 中使用 Astra 构建浏览器程序化太空游戏 Void Explorer 的过程。玩家可以在数千个恒星系统之间航行，从太空接近行星、进入大气层、着陆、离开飞船步行，再回到飞船起飞。

Ricouard 从玩家体验和生成式视觉参考开始。Astra 提出应用架构，使用 TypeScript、Vite 和 Three.js，把渲染器迁移到 WebGPU，并以 Node Material 和 Three.js Shading Language 构建大气、水面、光照等效果。Web Worker 在后台准备地形几何体，Vitest 和 Playwright 则检查可重复生成、坐标行为、浏览器交互和完整游戏旅程。

原文解释了由 Seed 驱动的程序化行星、观察者相对坐标、多级细节、共享地形函数、流式地形加载、碰撞就绪状态、大气与云层如何在连续下降过程中协同工作。文章还报告 Proxy 几何体、Mesh 数据传输、废弃地形任务、Draw Call、三角形数量和无头浏览器帧间隔的受控测量，并明确说明这些测试能够与不能衡量什么。

Astra 还把概念图转换为 Blender 飞船资产，并将导出模型接入程序化世界。另两个项目 Sunwake 与 Hollowflux 都把程序化水体同时用作视觉和玩法系统。文章最后介绍了通过 Sites 插件发布浏览器游戏的简单路径，并链接三款游戏的可玩版本。

文章给出较丰富的实现证据，也明确说明 Heightfield 地形的限制，以及软件渲染测试时间与硬件帧率的区别。它仍然是一名创作者的案例，不能证明其他团队和游戏类型也会获得相同的生产率、成本或可靠性。
